## v0.20.1 — ReadWriteOnce fencing across nodes

### Fixed

- **RWO volumes could be mounted on two nodes during a drain** ([#291](https://github.com/fenio/tns-csi/issues/291)). The CSIDriver declared `attachRequired: false`, so Kubernetes never created VolumeAttachments and never ran its Multi-Attach check. An evicted pod's replacement could stage an iSCSI or NVMe-oF volume on another node before the old node had unstaged it, and ext4 on both nodes could corrupt the filesystem. The chart now sets `attachRequired: true` (chart value `csiDriver.attachRequired`), and the new node waits for the old node to detach.
- `ControllerPublishVolume` no longer checks the node against an in-memory registry outside test mode. That registry is only filled when the controller and node services share a process (csi-sanity), so in a real deployment every publish would have failed with `NotFound` once attach was enabled.

### Upgrade notes

- **`attachRequired` is immutable.** Delete the CSIDriver object before running `helm upgrade`: `kubectl delete csidriver tns.csi.io`. Running pods keep their mounts. The chart stops the upgrade with these instructions if you forget. See [CSIDriver attachRequired change](../DEPLOYMENT.md#csidriver-attachrequired-change-v0201).
- Don't drain nodes or reschedule storage-backed pods during the upgrade.
- **Volumes that were already mounted are not fenced until they are mounted again, or until the node's kubelet restarts.** The kubelet only lists a volume in `status.volumesInUse`, which the attach/detach controller relies on to wait for unstage, if the volume was mounted while attach was required. Until then, moving that volume to another node is still exposed to the original race. [The upgrade guide](../DEPLOYMENT.md#volumes-mounted-before-the-upgrade-are-not-yet-fenced) has a check that lists unfenced volumes and two ways to fix them without moving pods. Don't drain nodes until the check is clean.
- VolumeAttachments for existing volumes appear on the attach/detach controller's next periodic rescan, typically within a couple of minutes after the upgrade, not immediately.
- With Helm 4, pass `--force-conflicts` if Flux or another server-side-apply tool also manages the release. Otherwise the upgrade can fail after the new CSIDriver is created, and the old controller then rejects every attach until the upgrade is re-run.
- NFS and SMB volumes also get VolumeAttachments now. Publishing them is a no-op, so the only effect is a short attach step before mount.
- Deleting a PVC right after its pod now takes a few seconds longer: the provisioner waits for the VolumeAttachment to be removed before calling `DeleteVolume`, and logs `VolumeFailedDelete ... is still attached to node` while it waits. This is expected.
- **Behavior change when a node crashes:** a replacement pod no longer mounts an RWO volume while the old pod is still `Terminating` on the unresponsive node. It waits with a `Multi-Attach error` until the node comes back, the node gets the `node.kubernetes.io/out-of-service` taint, or the old pod is force-deleted. Use the last two only on a node you know is powered off: the driver does not yet revoke the old node's access on TrueNAS ([#299](https://github.com/fenio/tns-csi/issues/299)). See [Nodes that crash or become unreachable](../DEPLOYMENT.md#nodes-that-crash-or-become-unreachable).
- **Volumes that moved between nodes before the upgrade may have hidden ext4 damage** that only shows up when the damaged metadata is next used. An offline `e2fsck -fn` is the only reliable check. See [the upgrade guide](../DEPLOYMENT.md#volumes-that-moved-between-nodes-before-the-upgrade-may-be-damaged).
