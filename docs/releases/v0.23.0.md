## v0.23.0 — riding out network outages, online iSCSI expansion, and TrueNAS 27 login

This release lets iSCSI and NVMe-oF volumes survive longer network interruptions, fixes online expansion of iSCSI volumes, and adds the login TrueNAS 27 asks for. No manual upgrade step is needed, but read **Preparing for TrueNAS 28** below: the API key login the driver uses today is deprecated.

The images are also built with Go 1.27.4, which fixes GO-2026-6859 in `net/http`. v0.22.0 was built with 1.27.3.

### Preparing for TrueNAS 28

TrueNAS 27 deprecates `auth.login_with_api_key`, and its version notes plan to remove it in 28. Once it's gone, a driver still using it can't log in, and the controller and node pods crash-loop. Set the TrueNAS user that owns your API key and the driver logs in with `auth.login_ex` instead, which works from TrueNAS 25.10 on ([#335](https://github.com/fenio/tns-csi/pull/335), [#343](https://github.com/fenio/tns-csi/pull/343)):

```yaml
truenas:
  username: truenas_admin   # the user the API key belongs to
```

- With a chart-managed Secret, `helm upgrade` restarts the pods so they pick it up.
- With `truenas.existingSecret`, add a `username` key to your Secret, then run `kubectl rollout restart` on the controller Deployment and node DaemonSet.
- Without a username nothing changes: the driver keeps using the old login and logs a warning at startup.
- The kubectl plugin reads `username` from the same Secret as the key, or `TRUENAS_API_USERNAME` alongside `TRUENAS_API_KEY`.

### Added

- **Session timeouts for network interruptions** ([#326](https://github.com/fenio/tns-csi/issues/326), [#327](https://github.com/fenio/tns-csi/pull/327)). When a node loses TrueNAS for longer than its session timeout, queued I/O fails, ext4 aborts its journal and the mount stays read-only until the pod restarts. The defaults (120 s for iSCSI, 60 s for NVMe-oF) are shorter than some switch or router reboots. Two node-wide chart values raise them:
  - `node.iscsiReplacementTimeout` (default `0`, the host's 120 s) sets open-iscsi's `replacement_timeout` before each login. It also raises the disk's SCSI command timeout to a fifth of it. Otherwise the kernel still fails a command that has been pending for more than 180 s after the session reconnects.
  - `node.nvmeCtrlLossTimeout` (default `60`, the value used so far; `-1` retries forever) is passed to `nvme connect --ctrl-loss-tmo`.

  Both apply at login or connect, so a staged volume picks up a change after a full unstage. The trade-off is that I/O and unmounts hang that long during a real TrueNAS outage. See [DEPLOYMENT.md](https://github.com/fenio/tns-csi/blob/v0.23.0/docs/DEPLOYMENT.md).
- **Metrics for the iSCSI node database:** `tns_csi_iscsiadm_waiting` and `tns_csi_iscsi_stale_db_lock_recoveries_total` ([#337](https://github.com/fenio/tns-csi/pull/337)). See [METRICS.md](https://github.com/fenio/tns-csi/blob/v0.23.0/docs/METRICS.md).

### Fixed

- **Online iSCSI expansion did not grow the filesystem** ([#328](https://github.com/fenio/tns-csi/issues/328), [#342](https://github.com/fenio/tns-csi/pull/342)). The zvol grew and Kubernetes reported `FileSystemResizeSuccessful`, but the node never told the kernel the disk had grown, so `resize2fs` had nothing to do. The node plugin now rescans the disk and waits for the new size before resizing, and asks the kubelet to retry instead of reporting success if the size doesn't change. This also applies to raw block volumes. Volumes expanded while unattached were not affected. A PVC that already went through a failed online expansion needs another expansion to grow its filesystem.
- **iSCSI staging could leave open-iscsi's node database locked** ([#336](https://github.com/fenio/tns-csi/issues/336), [#337](https://github.com/fenio/tns-csi/pull/337)). A timed-out `iscsiadm` was killed while holding `/run/lock/iscsi/lock.write`, and every later iSCSI operation on the node failed with "Timeout on acquiring lock on DB" until someone removed the file. Now:
  - The node plugin runs node-database operations one at a time per node and no longer kills them mid-write.
  - It removes a lock left by a process that died, but only when it can see the host's processes (`hostPID`, as the chart sets) and no possible owner is alive.
  - `mkfs` and `resize2fs` are no longer killed part way. A request that outlives its deadline returns `Aborted`, and the volume is not unstaged under the running command.
- **NVMe-oF staging kept sleeping after its request was cancelled** ([#337](https://github.com/fenio/tns-csi/pull/337)).
- **On HA TrueNAS, the standby's `REDIRECT` login response is no longer reported as a rejected API key** ([#343](https://github.com/fenio/tns-csi/pull/343)).

### Behaviour changes

- A slow `mkfs`, `resize2fs` or `iscsiadm` that outlives the kubelet's deadline is no longer killed at that deadline, and the retry returns `Aborted` until the command finishes. Only a much longer hard ceiling (minutes) still kills a command that is truly hung. Before, the deadline killed it, which could leave a half-written filesystem or the lock above.

### Documentation

- A volume with regular (non-detached) snapshots is not deleted until its snapshots are removed: the PV stays `Released` meanwhile. The docs said the snapshots were deleted with the volume ([#325](https://github.com/fenio/tns-csi/issues/325), [#341](https://github.com/fenio/tns-csi/pull/341)).

### Changed

- Built with Go 1.27.4 (GO-2026-6859). CSI spec updated to v1.14.0, `golang.org/x/sys` to v0.50.0, `golang.org/x/sync` to v0.25.0.
- Dashboard: search inputs are labelled, volume rows open from the keyboard, and htmx is pinned with Subresource Integrity ([#324](https://github.com/fenio/tns-csi/pull/324)).
