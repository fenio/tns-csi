## v0.21.0 — ReadWriteOnce fencing across nodes

The main change fixes [#291](https://github.com/fenio/tns-csi/issues/291): an RWO iSCSI or NVMe-oF volume could be mounted read-write on two nodes at once during a drain, which corrupted ext4. The fix is in [#295](https://github.com/fenio/tns-csi/pull/295). It changes how volumes attach and needs a manual step to upgrade, so read **Before you upgrade** first.

### Before you upgrade

- **`attachRequired` is immutable, so delete the CSIDriver object first:** `kubectl delete csidriver tns.csi.io`, then run `helm upgrade`. Running pods keep their mounts. If you forget, the chart stops the upgrade and prints these instructions. Don't drain nodes or reschedule storage-backed pods during the upgrade. See [CSIDriver attachRequired change](https://github.com/fenio/tns-csi/blob/v0.21.0/docs/DEPLOYMENT.md#csidriver-attachrequired-change-v0210).
- **Volumes that were already mounted are not protected until they are mounted again.** The kubelet decides whether a volume needs fencing when it first mounts it, so volumes mounted before the upgrade stay exposed to the original race when they move to another node. [The upgrade guide](https://github.com/fenio/tns-csi/blob/v0.21.0/docs/DEPLOYMENT.md#volumes-mounted-before-the-upgrade-are-not-yet-fenced) has a check that lists them, and two ways to fix them without moving pods: restart each pod on its current node, or restart the kubelet one node at a time. The kubelet restart has not yet been tested on a real cluster, so prefer the pod restart. Don't drain nodes until the check prints nothing.
- **Volumes that moved between nodes before the upgrade may have hidden ext4 damage.** It can stay invisible for days, until the damaged metadata is next used. An offline `e2fsck -fn` is the only reliable check. See [the upgrade guide](https://github.com/fenio/tns-csi/blob/v0.21.0/docs/DEPLOYMENT.md#volumes-that-moved-between-nodes-before-the-upgrade-may-be-damaged).
- **Behavior change when a node crashes:** a replacement pod no longer mounts an RWO volume while the old pod is still `Terminating` on the unresponsive node. It waits with a `Multi-Attach error` until the node comes back, the node gets the `node.kubernetes.io/out-of-service` taint, or the old pod is force-deleted. Use the last two only on a node you know is powered off: the driver does not yet revoke the old node's access on TrueNAS ([#299](https://github.com/fenio/tns-csi/issues/299)). See [Nodes that crash or become unreachable](https://github.com/fenio/tns-csi/blob/v0.21.0/docs/DEPLOYMENT.md#nodes-that-crash-or-become-unreachable).

### Added

- **`mkfsOptions` StorageClass parameter** ([#300](https://github.com/fenio/tns-csi/issues/300), [#304](https://github.com/fenio/tns-csi/pull/304)): extra `mkfs` options for newly formatted NVMe-oF and iSCSI volumes. For example, `mkfsOptions: "-O mmp"` turns on ext4 multi-mount protection, so the kernel refuses a second read-write mount from another node. Only options that cannot point `mkfs` at another device or a node file are accepted. See the [chart README](https://github.com/fenio/tns-csi/blob/v0.21.0/charts/tns-csi-driver/README.md).

### Fixed

- **RWO volumes could be mounted on two nodes during a drain.** The CSIDriver declared `attachRequired: false`, so Kubernetes never created VolumeAttachments and never ran its Multi-Attach check. An evicted pod's replacement could stage an iSCSI or NVMe-oF volume on another node before the old node had unstaged it, and ext4 on both nodes could corrupt the filesystem. The chart now sets `attachRequired: true` (chart value `csiDriver.attachRequired`), and the new node waits for the old node to detach.
- `ControllerPublishVolume` no longer checks the node against an in-memory registry outside test mode. That registry is only filled when the controller and node services share a process (csi-sanity), so in a real deployment every publish would have failed with `NotFound` once attach was enabled.
- **Volume capacity metrics are no longer empty after a controller restart** ([#298](https://github.com/fenio/tns-csi/issues/298), [#303](https://github.com/fenio/tns-csi/pull/303)). The controller rebuilds `tns_csi_volume_capacity_bytes` from TrueNAS on start and every 5 minutes, and drops volumes deleted outside Kubernetes. Cloned and adopted volumes now use the same `volume_id` label as other volumes, so deleting them no longer leaves a stale series.
- **The bundled Grafana dashboard showed `Datasource ${DS_PROMETHEUS} was not found` on every panel** when Grafana loaded it through file provisioning ([#296](https://github.com/fenio/tns-csi/pull/296)). The dashboard now defines its Prometheus datasource variable itself.

### Documentation

- The iSCSI prerequisites now say that the host's open-iscsi must be the same version as the image's (2.1.12). On Talos that means v1.13.9 or later ([#194](https://github.com/fenio/tns-csi/issues/194), [#302](https://github.com/fenio/tns-csi/pull/302)).

### Other upgrade notes

- VolumeAttachments for existing volumes appear on the attach/detach controller's next periodic rescan, typically within a couple of minutes after the upgrade, not immediately.
- With Helm 4, pass `--force-conflicts` if Flux or another server-side-apply tool also manages the release. Otherwise the upgrade can fail after the new CSIDriver is created, and the old controller then rejects every attach until the upgrade is re-run.
- NFS and SMB volumes also get VolumeAttachments now. Publishing them is a no-op, so the only effect is a short attach step before mount.
- Deleting a PVC right after its pod now takes a few seconds longer: the provisioner waits for the VolumeAttachment to be removed before calling `DeleteVolume`, and logs `VolumeFailedDelete ... is still attached to node` while it waits. This is expected.
- To keep the previous behavior, set `csiDriver.attachRequired=false`. The same delete-and-upgrade steps apply.
