## v0.22.0 — iSCSI fencing and reliability fixes

The main addition is opt-in iSCSI fencing ([#299](https://github.com/fenio/tns-csi/issues/299), [#315](https://github.com/fenio/tns-csi/pull/315)). When Kubernetes detaches an iSCSI volume from a node, the driver now revokes that node's access on TrueNAS, so a node that is partitioned rather than powered off can no longer write to a volume that has moved elsewhere. This release also contains a large set of reliability fixes for retried and interrupted operations ([#309](https://github.com/fenio/tns-csi/pull/309)). No manual upgrade step is needed. Fencing stays off unless you enable it.

### Added

- **iSCSI fencing** (`fencing.enabled`, off by default). Each node registers an initiator group with its own IQN on TrueNAS. Publishing a volume restricts its target to the publishing node's group, and unpublishing removes it, so detaching a volume from an unreachable node cuts that node off on TrueNAS before the volume is attached anywhere else. TrueNAS keeps the old session logged in but rejects every I/O on it. This makes the `node.kubernetes.io/out-of-service` taint safe for iSCSI volumes even when the node may still be running. Requirements and limits:
  - It needs `csiDriver.attachRequired: true` (the default since v0.21.0), and the chart refuses it otherwise.
  - Every node needs a unique initiator name. Publishing to a node whose IQN another node also reports fails with `FailedPrecondition`.
  - Existing volumes are fenced from their next publish, i.e. after a full unstage.
  - NVMe-oF, NFS and SMB volumes are not fenced.

  Verified on a 3-node cluster with a partitioned node that kept writing: detach, fence and attach on the new node took about 2 s, and no write from the old node reached the disk after the fence. See [FENCING.md](https://github.com/fenio/tns-csi/blob/v0.22.0/docs/FENCING.md).
- **`node.healthPort`** chart value for the node plugin's liveness port (default `9808`). The node plugin uses the host network, so a second release on the same nodes needs its own port ([#317](https://github.com/fenio/tns-csi/issues/317)).

### Fixed

- **Volumes with ext4 MMP could not move to another node after a crash** ([#316](https://github.com/fenio/tns-csi/pull/316)). After an unclean unmount, an MMP filesystem waits about twice its check interval before mounting (~42 s measured). The driver killed iSCSI and NVMe-oF staging mounts after 30 s, so every retry restarted the wait and the pod never started. Staging mounts now get 100 s. This affected anyone using `mkfsOptions: "-O mmp"` since v0.21.0, with or without fencing.
- **A custom `csiDriverName` was ignored by the plugin and the StorageClasses** ([#316](https://github.com/fenio/tns-csi/pull/316)). The chart didn't pass `--driver-name`, so a second release registered with the kubelet as `tns.csi.io` and took over the first release's registration on every node. Its StorageClasses also named `tns.csi.io` as the provisioner. Both now use `csiDriverName`.
- The node plugin no longer mounts `/var/lib/tns-csi` from the host. Nothing has used it since the format registry was removed, and it was shared between releases ([#317](https://github.com/fenio/tns-csi/issues/317)).
- Reliability fixes from an audit of retried, timed-out and interrupted operations ([#309](https://github.com/fenio/tns-csi/pull/309)). Each one has a test that failed before the fix:
  - **TrueNAS client:**
    - A lost response to the iSCSI reload after creating a volume no longer restarts the iSCSI service, which dropped every iSCSI session on the box.
    - The client reconnects after about a minute without pongs instead of hanging until the pod is restarted.
    - Waiting on a replication job that middlewared no longer knows (e.g. after a restart) fails at once instead of waiting out the request deadline.
    - Requests in flight when the connection drops fail immediately instead of after the reconnect backoff.
  - **Retried CreateVolume** now converges instead of leaving the PVC Pending:
    - NVMe-oF ("subsystem already exists").
    - Clones from a snapshot or a volume.
    - NFS: the export is recorded, so it is removed on delete.
    - SMB: the ACL is re-applied.
    - Detached clones and detached snapshots: a running replication is continued and a finished one kept, rather than restarted. A detached snapshot is no longer reported ready while its copy is still running.
  - **Cleanup after a failed create** now runs on a context of its own, so it no longer leaves orphaned zvols, subsystems, shares or datasets when the request has timed out.
  - **NFS/SMB DeleteVolume** keeps the dataset and returns `Unavailable` when the share delete fails, instead of orphaning the export.
  - **NVMe-oF:** a kubelet restart no longer disconnects a subsystem whose namespace is still mounted, which left a dead mount under a running pod.
  - **Adoption:**
    - iSCSI adoption honours the StorageClass's `portalId`/`initiatorId` and checks that the extent backs the right zvol.
    - Adopted NFS/SMB volumes are sized with `refquota`, like created ones.
  - `ControllerUnpublishVolume` with an empty node ID unpublishes from every node, as the CSI spec requires.

### Behaviour changes

- An existing NFS or SMB dataset at a volume's path without `managed_by=tns-csi` now returns `AlreadyExists` instead of being reused silently.
- iSCSI adoption is stricter. An extent backing another disk, a mapping other than LUN 0, or extra mappings return `AlreadyExists`.
- SMB returns `AlreadyExists` on a capacity mismatch, like NFS.
- With fencing on, the driver manages each iSCSI target's initiator groups itself. An `initiatorId` StorageClass parameter only applies until the volume is first published.

### Changed

- Kubernetes client libraries updated to v0.37.2 ([#312](https://github.com/fenio/tns-csi/pull/312)).
- Dashboard dependency `qs` updated to 6.17.0 ([#313](https://github.com/fenio/tns-csi/pull/313)).

### Documentation

- The remedy for volumes left unfenced by the v0.21.0 upgrade is corrected. Wait for the node plugin's logout line, not for the VolumeAttachment to go, before scaling back up. Both remedies are now verified by a cross-node e2e suite ([#309](https://github.com/fenio/tns-csi/pull/309), [#311](https://github.com/fenio/tns-csi/pull/311)).
- New [FENCING.md](https://github.com/fenio/tns-csi/blob/v0.22.0/docs/FENCING.md). It covers the out-of-service taint recipe and ext4 MMP as defence in depth.
